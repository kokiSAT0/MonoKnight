# MonoKnight Collaboration Workflow

本書は、GitHubとCodexを使った共同開発の運用ルールを定める。
実装・検証の詳細は [`dev-workflow.md`](dev-workflow.md)、最上位判断は [`../AGENTS.md`](../AGENTS.md) を正本とする。

## 1. 役割

- リポジトリオーナー: `kokiSAT0`
- 共同開発者: `Kurohyou3`
- `main` への最終採用判断とマージはリポジトリオーナーが行う

## 2. 作業開始

1. `main` の最新状態を取得する
2. 最新の `origin/main` から `codex/<作業名>` ブランチを作る
3. Codexに `AGENTS.md`、`docs/index.md`、関連する正本を最初に読ませる
4. 大きなデザイン・世界観変更は、早い段階で `main` 向けDraft PRを作る

共同開発者は `main` へ直接pushしない。

## 3. 実験的なデザイン変更

- 大胆な変更は実験ブランチ内で行い、採用前の `main` は変更しない
- PRには目的、変更範囲、判断してほしい点を明記する
- UI変更はスクリーンショットまたは動画を添付する
- デザイン、世界観、ゲーム仕様の変更は可能な範囲でコミットを分ける
- 画像、フォント、音源などは、利用許諾と出典をPRに記載する
- ゲーム仕様や構成も変える場合は関連docsを同じPRで更新する

## 4. 検証とレビュー

- 変更に合う検証を [`dev-workflow.md`](dev-workflow.md) に従って実行する
- 実施した検証と、未実施の検証があればその理由をPRへ記載する
- `main` へのPRはリポジトリオーナーの承認後にマージする
- 実験中はDraftのままにし、採用判断の準備ができたらReady for reviewへ変更する

## 5. 採用と取りやめ

- 採用する場合は、原則としてGitHub上でPRをマージする
- 採用しない場合はPRを閉じ、実験ブランチを削除する。`main` に復元操作は不要
- マージ後に取り消す場合は履歴を書き換えず、GitHubのRevertで打ち消すPRを作る
- force pushや履歴の書き換えで `main` を戻さない

## 6. ブランチの扱い

- ブランチ名は `codex/<短い作業名>` を基本とする
- 1ブランチには1つの目的だけを含める
- マージ済み、または不採用となったブランチは削除する
- 長期実験では定期的に `main` の変更を取り込み、競合を小さいうちに解消する
